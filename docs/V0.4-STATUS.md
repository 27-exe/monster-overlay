# v0.4 Status

Status snapshot for the v0.4 release. Replaces the v0.2 status
document (`docs/V0.2-STATUS.md`) which is kept for historical
reference only.

## What shipped in v0.4

### Per-panel section masks (`--mask-*`)

`monster-overlay` now accepts three hex32 bitmask flags:

| flag                  | panel  | mask bits                                  |
|-----------------------|--------|------------------------------------------|
| `--mask-player <hex>`  | player | Conn, Quest, Weapon, Bars, Mantles, Debuff |
| `--mask-monster <hex>` | monster | Info, Hp, Enrage, Ail, Parts              |
| `--mask-damage <hex>`  | damage | Rows, Share, Chart                        |

Default `0xFFFFFFFF` (all-on) matches legacy behaviour. Each
`MaskXxx` constant is exposed in `panel_sections.h` so callers
can compose masks without knowing the bit layout.

Bit layout is defined in [`src/ui/panel_sections.h`](../../src/ui/panel_sections.h).

### Master visibility (`--no-*`)

Three boolean flags disable an entire panel:

| flag         | effect                                       |
|--------------|----------------------------------------------|
| `--no-player` | player panel set to `panelEnabled_ = false` |
| `--no-monster` | monster panel set to `panelEnabled_ = false` |
| `--no-damage`  | damage panel set to `panelEnabled_ = false`  |

`panelEnabled_` is sticky. When false, `Panel::setVisible(true)`
is overridden by the implementation in `Panel::setVisible` so the
process never paints, the layer-shell surface never maps, and the
panel contributes zero pixels and zero height to the layout.

This is the behavioural distinction made explicit by 920c05e:

- **all sections off (`mask = 0`)** — the panel is alive, content
  is empty, layer-shell surface is mapped with minimum height. The
  panel name + a few sentinel rows remain visible. This is the
  "enable panel, but every sub is off" state.
- **master off (`--no-…`)** — the panel is unmapped. The widget
  is alive in memory but invisible; `kill(pid, 0)` polling in
  `monster-control` still tracks the overlay correctly.

### Control console (`monster-control`)

A standalone Qt GUI that owns a sub-process of `monster-overlay` and
provides masks + master toggles per panel. See
[`docs/CONTROL_CONSOLE.md`](CONTROL_CONSOLE.md) for the full
specification.

In v0.4 the console:

- Spawns `monster-overlay` via `QProcess::startDetached` with the
  currently-selected mask as `--mask-*` flags.
- Hides the console window on launch; the overlay takes the screen.
- Watches the overlay PID with `kill(pid, 0)` every 250 ms; on
  exit, re-shows the console.
- Persists the toggle state to `~/.config/monster-overlay/monster-overlay.conf`
  using the XDG path (`QStandardPaths::GenericConfigLocation`).
- Snaps the chrome back in when the close button is pressed (the
  three preview panels are top-level QMainWindow instances that are
  explicitly hidden + deleted in `~ControlPanel` and `closeEvent`).

### Build & hook system

- `ControlPanel` owns three off-screen preview panels driven
  using `WA_DontShowOnScreen + show()` so the live paint path
  runs (same QPainter code as monster-overlay) without mapping a
  wayland surface. `ControlPanel::renderPreview` then grabs the
  result into a `QPixmap` displayed by the right-column tiles.
- Tests:
  - `monster-control-l2-smoke` — round-trip mask persistence: open
    console, flip switches, exit, re-open, verify state restored.
  - `mhw-snap-player-demo` / `mhw-snap-all-demo` — offscreen
    pixel diff baselines (used during refactors to verify the
    block-table rewrite preserves the rendered output bit-for-bit).

## Architecture overview

```
                 ┌──────────────────────────────┐
                 │         monster-control           │
                 │   (QMainWindow, Qt 6)          │
                 │                                 │
                 │   preview─┐    ┌─────────────┐ │
                 │   panel ─┤    │  SectionRow │ │
                 │   tiles  │    │  ToggleChip │ │
                 │          │    └─────────────┘ │
                 │   right  │   ┌──────────────┐  │
                 │   Stack  │   │  SidePanelCard│ │
                 │          │   └──────────────┘  │
                 └─────────┬─┴──────────────────┘
                           │  QProcess::startDetached
                           ▼
                 ┌──────────────────────────────┐
                 │         monster-overlay            │
                 │   (layer-shell Qt 6)           │
                 │                                 │
                 │  PlayerPanel (TopLeft)         │
                 │  MonsterPanel (TopRight)       │
                 │  DamagePanel  (BottomRight)    │
                 │                                 │
                 │  reads /proc/<pid>/mem         │
                 └────────────────────────────────┘
```

The control console (top) is a normal Qt window. The overlay
(bottom) is a KDE Wayland layer-shell surface — three independent
panels anchored to screen corners. They're separate processes so
the user's choice of toggles in the console always represents a
fresh overlay launch (no live mask sync from console to overlay).

## v0.5 notes (not shipped)

The v0.5 redesign attempt (3-column layout with sidebar,
compact hero, wide preview) was rolled back before reaching
publishable state. The widget prototypes
(`src/ui/sidebar_card.{h,cpp}`) are kept in `/tmp/v05_backup/`
for the next iteration. The HTML design mock
(`monster-overlay-concept .html`) remains the visual target.

The next iteration should focus on Phase A only — 3-column layout
with the existing `buildGroup` widgets — and stop there. Visual
polish (icons, density, hero) is a separate Phase B that can be
deferred.
