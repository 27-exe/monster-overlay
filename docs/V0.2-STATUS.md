> Snapshot at 2026-07-25. Previous data-layer parity (v0.1) covered monster
> HP / parts / ailments / enrage, player HP/ST / mantles, party damage,
> quest, zone. v0.2 focused on **UI rebuild** — three independent panels,

## v0.2 — what shipped

### Three independent Wayland layer-shell panels

| Panel         | Anchor corner | Content                                                |
|---------------|---------------|--------------------------------------------------------|
| PlayerPanel   | TopLeft       | HP / ST bars + mantles + weapon icon                   |
| MonsterPanel  | TopRight      | First live large monster HP + per-part HP / status     |
| DamagePanel   | BottomRight   | Party damage list + percentage bars                    |

- **Anchor + margins positioning.** Wayland layer-shell has no
  `move(x, y)`. Position is `setAnchors(corner) + setMargins(edge_offsets)`.
  See [Critical Wayland learnings](#critical-wayland-learnings) for
  why every mouse-based drag attempt failed.
- **Keyboard-based positioning** (`Panel::keyPressEvent`):
  - `←↑↓→` nudge 10 px
  - `Shift + arrows` nudge 50 px
  - `Ctrl + S` persist margins to QSettings
  - `Wheel` adjust scale (0.5x – 2.0x)
- **Edit mode (`--edit`)**:
  - All three panels visible with sample/demo content (`paintDemo`)
  - Dashed cyan border for visibility
  - `KeyboardInteractivity::OnDemand` so panels receive arrow keys
  - The `Panel::update(Data)` overloads shadow `QWidget::update()`, so
    external callers (e.g. main loop) must use `triggerUpdate()`.
- **Persistence**: `~/.config/mhw-linux-overlay/panels.ini` (QSettings
  INI format). Keys: `margins`, `scale`, `opacity`, `anchor`, `visible`.
- **Demo content** (when `--edit` is used without game data):
  player shows HP/ST bars + mantle slots + weapon placeholder;
  monster shows HP bar + sample parts (head/tail/wings);
  damage shows 4 sample party members with damage bars.

### Bug fixes that mattered for v0.2

| Bug                       | Root cause                                                                                          | Fix                                                                                                                  |
|---------------------------|-----------------------------------------------------------------------------------------------------|----------------------------------------------------------------------------------------------------------------------|
| 99.7 % CPU idle           | `MhwReader::findGamePid()` cached hits only when the PID was **found**; on miss it scanned `/proc` on every poll (16 ms × every proc) | Also cache the "not found" state for 5 s. Same throttle, same answer.                                                 |
| 100 %-screen lockup       | layer-shell surface without `setAnchors()` covers the whole output and steals input                   | Always call `setAnchors()` in `applyGeometry()`, **before** `QWidget::show()` (avoids "already has shell integration"). |
| Drag lag (until next click) | `setMargins()` only **requests** compositor reposition; the surface commits a frame only on `update()` | Repaint on the main poll loop tick (`triggerUpdate()` in main loop, no inline `update()` in mouse handlers).          |
| Drag flicker (oscillation)| See below — every mouse-event-based drag scheme hit a feedback loop                                | Killed all mouse-event dragging. Replaced with keyboard nudge + compositor-only coordinate reads.                     |

## Critical Wayland learnings

### Drag feedback loop (the one that ate a day)

Every approach to dragging a `LayerShellQt::Window` by mouse hit the
same feedback loop:

1. `mouseMoveEvent` reads cursor position.
2. `setMargins(m)` requests the compositor reposition the surface.
3. The compositor moves the surface **before** the next event arrives.
4. Qt's next cursor-coordinate read is stale or computed from the
   new surface geometry — and inconsistent across the schemes tried.

Schemes we abandoned, all with the same symptom:

| Scheme                                | Symptom                                              |
|---------------------------------------|------------------------------------------------------|
| `globalPosition() - pressGlobal` cumulative | Overshoots with distance; panel ends up off-screen |
| `globalPosition() - lastGlobalPos` per-frame delta | Flickers; closer-to-cursor / closer-to-origin alternation |
| `e->position()` (local) drift correction | Same as cumulative — local pos is also stale after `setMargins` |
| `QCursor::pos()` polled at 16 ms      | Worked in theory but ran the main loop at 60 Hz and pegged one CPU core from the proc scan alone. Also intermittently wrong. |

**Resolution**: drop mouse-event dragging entirely. Use keyboard nudge.
If the user later needs fluid drag, the only sane Wayland-native path is
to move the surface to the **anchor-only** state and use a
**layer-shell exclusive zone** to position it via `KDE`'s window-position
API — but that's an external compositor contract, not a per-frame loop.

### Other Wayland constraints observed

- **Surface must be configured before `show()`**, or Qt logs "already
  has a shell integration" and the second `get(windowHandle)` is a
  no-op. Constructor order in `Panel`: `applyGeometry()` → `loadConfig()`,
  then main.cpp calls `setVisible(true)` last.
- **`setDesiredSize` is non-zero or undefined**: an unset desired size
  makes the surface take its layout size, which for `QMainWindow` can
  be 0. Always call `setDesiredSize(QSize(w*scale, h*scale))` in
  `applyGeometry()`, and guard against no-op calls when size is unchanged
  to avoid endless repaint storms.
- **`KeyboardInteractivity::None` swallows all pointer events** — no
  drag, no focus. Edit mode needs `OnDemand`.
- **`update()` from mouse handlers floods**: the main poll timer (60 Hz
  in edit mode) already provides periodic commits; per-event `update()`
  on top of that produces a paint storm. The final design has the
  mouse handlers only call `setMargins()`; `triggerUpdate()` is called
  solely by the poll timer.

## Open items / v0.3 candidates

- **Multi-monster MonsterPanel** — currently shows the first live
  monster only. Plan: vertical stack of N mini panels (one per
  large monster), each with HP + parts. Layout coordinator in
  `MonsterPanel` needs to allocate sub-rects.
- **DamagePanel → DPS chart** — currently a static table. Plan: a
  scrolling time-series chart of `damage/sec` per party member. Data
  path is fine (we already snapshot party damage on each poll); only
  the renderer needs to move from bars to a QPainter polyline.
- **DPR / HiDPI sizing** — `logicalSize_` × `scale_` gives window
  pixels; on a HiDPI screen the resulting surface is half physical
  pixels. Use `devicePixelRatio()` of the primary screen.
- **Mouse drag for `damagePanel` chart selector** — if we add an
  interactive chart, dragging inside one layer-shell window is fine
  (no surface motion, only internal). No wayland feedback loop there.
- **Auto-hide on screenshot / OBS capture** — `wlr-layer-shell-unstable-v1`
  has no `screencopy-aware` flag, but we can set opacity to 0 when
  a specific X11/Wayland property is set. Out of scope for v0.3.

## How to verify v0.2 (manual)

```bash
cmake --build build -j$(nproc)

# 1. Demo without game — verify all three panels visible
QT_QPA_PLATFORM=wayland ./build/mhw-overlay --edit --poll 250

# 2. Nudge PlayerPanel
#    click it (focus), press ← ↑ → ↓ (each 10 px) / Shift + arrows (50 px)
#    press Ctrl+S to persist; check ~/.config/mhw-linux-overlay/panels.ini

# 3. Live test
#    start MHW under Proton, then:
QT_QPA_PLATFORM=wayland ./build/mhw-overlay --poll 250
```
