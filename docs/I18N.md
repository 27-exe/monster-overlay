# i18n — adding strings and locales

All UI text on the overlay comes from `src/resources/i18n/<locale>.json`,
loaded by `mhw::StringTable` at startup. The C++ side has **zero
hardcoded UI strings** outside the demo baseline (and the demo is
intentional — see below).

## Lookup from C++

Use the `mh::tr` namespace function:

```cpp
// src/overlay_window.cpp
namespace mh {
inline QString tr(const QString& key) {
    return mhw::StringTable::instance().tr(key);
}
}

// At any call site:
context_->setText(mh::tr("ui.context_hunting").arg(zoneName));
```

The macro form is intentionally not used — see ARCHITECTURE.md for why
`tr(...)` unqualified would resolve to `QObject::tr` via ADL on the
implicit `this`.

`tr("ui.context_hunting")` returns the **value** at the dot-path
`ui.context_hunting` in the loaded locale, or the key string itself
if the key is missing (so missing entries show up visibly in the
overlay as `ui.context_hunting` rather than rendering blank).

## Loading a locale

`main.cpp` parses `--locale <code>`. If the file isn't found,
`StringTable::load()` returns false and the singleton continues
serving empty entries. The overlay will then show dot-paths instead
of translations — useful for catching missing keys.

```bash
./build/monster-overlay --locale zh-CN   # default
./build/monster-overlay --locale en-US
./build/monster-overlay --locale ja-JP
```

## Adding a new string

1. Open `src/resources/i18n/zh-CN.json`.
2. Add a key to the relevant section:
   ```json
   "ui": {
       "new_section": {
           "new_key": "新文字 %1"
       }
   }
   ```
3. The dot-path is `ui.new_section.new_key`. Use it as
   `mh::tr("ui.new_section.new_key")` in C++.
4. Rebuild:
   ```bash
   cmake --build build
   ```
5. The new key is now in the binary. `StringTable::load` flattens
   nested objects on read; sub-objects become dot-paths.

**Don't** embed the translation in C++ even as a fallback —
"fallback in code" defeats the whole point of the JSON. If a
translation is missing, **fix the JSON**, not the code.

## Adding a new locale

1. Copy `src/resources/i18n/zh-CN.json` to `<new-code>.json`,
   e.g. `en-US.json`.
2. Translate every value. **Keep the keys (left side of `:`) in
   English / dot-path form** — they're identifiers, not content.
3. Rebuild. `StringTable::load` doesn't know about specific
   locales; it loads whatever file the user passes via `--locale`.

If the user passes `--locale en-US` and the file doesn't exist,
`StringTable::load` returns false and the overlay shows dot-paths.
That's the diagnostic. Fix: add the file.

If you want **fallback to a default locale** (e.g. fall back to
`zh-CN` if `en-US` is missing), edit `main.cpp`:

```cpp
if (!mhw::StringTable::instance().load(locale)) {
    qWarning() << "Locale" << locale << "not found, falling back to zh-CN";
    if (!mhw::StringTable::instance().load("zh-CN")) {
        qCritical() << "Built-in fallback zh-CN also missing; UI will show dot-paths.";
    }
}
```

This is **not** the current behaviour. v0.1 prefers the visible
diagnostic over a silent fallback — the user notices the missing
locale and fixes it.

## Schema conventions

| Section           | Purpose                                                  |
|-------------------|----------------------------------------------------------|
| `ui.*`            | UI strings (rendered via `mh::tr`)                     |
| `mantle.<int>`    | mantle labels keyed by HunterPie SpecializedToolType enum |
| `abnormality.*`   | player-side abnormality labels                          |
| `_meta.*`         | file metadata (loaded but unused at runtime)            |

The `mantle.<int>` numbering matches HunterPie 2.14.0.461's
`SpecializedToolType` enum (id 0..19). Adding a new mantle = add a
new key. Renaming an existing one is a HunterPie version bump; do
not do it casually.

### Why keys are dot-paths, not arbitrary strings

The `mh::tr("ui.context_hunting")` lookup is one `QHash::constFind`
call. The dotted key is just a string, no parser involved. The
JSON's nested structure is a **readability** feature for humans
editing the file; the loader flattens it once at startup.

If you find yourself wanting `mh::tr("ui")` and getting the whole
`ui` section back as a JSON document, **don't**. The string table
returns leaf strings only. If you need a structured payload,
add a domain reader and pass it through `GameSnapshot`.

## Pluralisation, gender, RTL

The current `QString::arg`-based interpolation does **not** support
ICU plural rules, gender agreement, or RTL bidi handling. The
expected audience is Chinese + English + a couple of Asian
locales, so this is acceptable. If you need full ICU, replace
`mhw::StringTable::tr` with a wrapper that takes ICU arguments and
plumbs them to Qt's `QString::arg` (which already supports `%L1` for
locale-aware numbers, but not grammatical gender).

## How the demo mode interacts with i18n

`OverlayWindow::renderDemo()` is a **regression baseline**: it
hardcodes the same text that the live path produces through `mh::tr`,
so any drift between "what the keys say" and "what the demo shows"
is a bug. If you change `ui.context_hunting` from `"狩猎 · %1"` to
`"[%1]"` and the demo's line still says `狩猎 · 古代树森林`, you
have a regression to fix.

The exception is the monster name: in live mode the name comes
from `monster.internalName` (already Id→zh-CN-translated by
`readMonsters`); in demo we hardcode `em\em100_00` so it's obvious
the demo isn't pulling from a real game.
