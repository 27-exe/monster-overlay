# i18n — adding strings and locales

All UI text in the overlay comes from a per-locale **directory** of JSON
domain files under `src/resources/i18n/<locale>/` (currently
`zh-CN/overlay.json`, `zh-CN/console.json`, `en-US/overlay.json`,
`en-US/console.json`), loaded by `mhw::StringTable` at startup. The C++
side keeps **zero hardcoded UI strings** — including the edit-mode demo
seed, which reads the same table (see "How the demo mode interacts with
i18n" below).

## Lookup from C++

Use the `mh::tr` namespace function:

```cpp
// src/ui/panel_player.cpp
namespace mh {
inline QString tr(const QString &key) {
    return mhw::StringTable::instance().tr(key);
}
}

// At any call site:
p.drawText(titleRect, Qt::AlignLeft | Qt::AlignVCenter,
           mh::tr("ui.player_panel_header"));
```

The macro form is intentionally not used — see ARCHITECTURE.md for why
`tr(...)` unqualified would resolve to `QObject::tr` via ADL on the
implicit `this`.

`tr("ui.context_hunting")` returns the **value** at the dot-path
`ui.context_hunting` in the loaded locale, or the key string itself
if the key is missing (so missing entries show up visibly in the
overlay as `ui.context_hunting` rather than rendering blank).

**Hot paths:** `tr()` is a single `QHash::constFind`. Panels call it from
`paintPanel()` at the draw site — that is what makes a locale switch
visible on the next repaint without any re-translation bookkeeping.
Strings cached at construction time (window titles, demo seeds) are the
exception and go through `Panel::retranslateUi()` instead — see
"Switching locale at runtime".

## Loading a locale

`main.cpp` resolves the startup locale with this priority:

1. `--locale <code>` (explicit override, e.g. for testing),
2. the `locale=` row of `~/.config/monster-overlay/monster-overlay.conf`
   (`mhw::readLocaleFromConf`, see `src/core/locale_conf.h`),
3. `zh-CN`.

```bash
./build/monster-overlay --locale zh-CN   # explicit override
./build/monster-overlay --locale en-US
./build/monster-overlay                  # conf value, else zh-CN
```

If the locale directory is missing, `StringTable::load()` returns false
and the singleton continues serving the previous table (empty before the
first successful load). A fresh start with an unknown locale therefore
shows dot-paths instead of translations — useful for catching missing
keys.

**Key parity is a hard requirement**: `en-US/*` must carry every key of
`zh-CN/*` and vice versa. Two audits live in `scripts/`:

```bash
python3 scripts/i18n_key_parity.py            # zh/en set equality (per file + merged)
python3 scripts/i18n_check_tr_keys.py         # every tr-style key used in src/ (+tests) exists
```

The second audit handles `QStringLiteral("key")` wrappers and the
`trSet`/`trTip`/`trHook`/`trWindowTitle` helpers, and checks *every*
locale directory — an en-only gap fails it.

## Switching locale at runtime (no restart)

The control console is the **sole writer** of
`~/.config/monster-overlay/monster-overlay.conf`; the overlay never writes
it. The console flips the `locale=` row (atomically, preserving the mask
rows) and the overlay picks it up from its paint loop:

```
main.cpp tick (every --poll ms, default 250 ms)
  └─ throttled to ~1 s → mhw::localeSyncPoll(state, confPath, active)
       ├─ no change → nothing (one mtime stat)
       └─ changed   → StringTable::load(next)
                      setWindowTitle(tr("ui.<panel>_title")) ×3
                      panel->retranslateUi() ×3   (cached strings + repaint)
```

Notes that matter when touching this path:

- `localeSyncInit()` primes the state from the current file **after** the
  startup decision, so a pre-existing conf value cannot undo `--locale`.
- **The console must not re-apply the conf locale in its constructor.**
  Startup precedence (`--locale` > conf > zh-CN) is owned by
  `main_control.cpp`; `ControlPanel`'s ctor guard only loads a locale when
  *nothing* is loaded yet. An extra `applyLocale(readLocaleFromConf())`
  there silently overrides an explicit `--locale` with a stale conf value
  and splits the UI (registered chrome re-translated, other widgets left
  on the CLI locale). Regression:
  `tests/control_l2_smoke.cpp` — "explicit-locale dominance over stale
  conf".
- The poll sits in front of the tick's exception barrier: a locale flip
  must land even if the game read path is throwing.
- `Panel::retranslateUi()` is the only re-translation entry point. The
  base implementation just repaints; panels override it to refresh what
  they cached (window title, demo seeds, `status_`).
- Panels re-run their demo seed on locale change (`resetDemoPrimed()`),
  so edit-mode previews follow the locale too. Live data is untouched —
  the reader republishes it on the next poll.
- Data-name tables — see the next section.

## Data-name tables (monsters / parts / zones / abnormalities)

Game-data names are **not** in the JSON files: they are zh/en C++ tables in
their home modules, switched at read time through
`mhw::StringTable::instance().isEnglish()` (readers re-resolve names every
poll, so a locale flip lands on the next snapshot — no restart, no cache).

| Domain | Location | en source |
|--------|----------|-----------|
| World monster names | `monster_reader.cpp` `monsterDisplayName()` | `en-us.xml Monsters/World` |
| World parts | `part_schemas.cpp` (`PartSchema::nameEn`, regen: `scripts/gen_schema.py --check/--in-place`) | `en-us.xml Monsters/Shared/Part` |
| Zones (World + Rise villages + RiseLoc) | `world_types.cpp` `zoneNameEn()` / `zoneNameLocalized()` | `en-us.xml Stages/{World,Rise}` |
| World monster ailments | `part_schemas.cpp` `kAilmentNamesEn` | HunterPie World data |
| World player abnormalities | `player_reader.cpp` (debuff/song/buff tables) + `playerDebuffName()` etc. | `en-us.xml Abnormalities` + HunterPie World AbnormalityData.xml |
| Rise monster names | `mhr_monster_names.cpp` (regen: `scripts/extract_rise_monster_names.py`) | `en-us.xml Monsters/Rise` |
| Rise parts | `mhr_part_names.cpp` (regen: `scripts/generate_rise_part_names.py`) | `en-us.xml Monsters/Shared/Part` |
| Rise abnormalities + ailment slots | `mhr_abnormalities.cpp` (regen: `scripts/extract_rise_abnormalities.py`) | `en-us.xml Abnormalities` |

Rules for touching these tables:

- **The zh column is frozen** for normal rows: regenerate/verify with
  `--check`; a zh diff is a regression (`git show HEAD:<file>` is the
  reference). The one exception is the `statePart` set — the 131 entries the
  reader never maps (state variants, `PART_UNKNOWN` sentinels, exotic enum
  entries). Those were cleaned to official zh-cn.xml names (v0.9 placeholder
  cleanup): `gen_schema.py` freezes `statePart` to the legacy
  `name.startsWith("PART_")` skip set, so the reader skip — and every
  normal-table slot index — is byte-identical to the pre-cleanup behaviour
  even though the names are real display strings now.
- English labels come from HunterPie's official localization
  (`en-us.xml`, pinned by sha256 in the file headers). The raw XMLs are
  not vendored; the generation scripts take paths as arguments.
- Raw `PART_*` enum ids no longer appear as display names anywhere: the
  reader skip is `PartSchema::statePart`, not a name test, so display
  filtering is language-independent by construction.

## Adding a new string

1. Open the domain file for the area you are touching —
   `src/resources/i18n/zh-CN/overlay.json` for the overlay panels,
   `zh-CN/console.json` for the control console.
2. Add a key to the relevant section:
   ```json
   "ui": {
       "new_section": {
           "new_key": "新文字 %1"
       }
   }
   ```
3. The dot-path is `ui.new_section.new_key`. Use it as
   `mh::tr("ui.new_section.new_key")` in C++.
4. Add the **same key** to every other locale directory (the parity
   script above is the check).
5. Rebuild:
   ```bash
   cmake --build build
   ```
6. The new key is now in the binary. `StringTable::load` flattens
   nested objects on read; sub-objects become dot-paths.

**Don't** embed the translation in C++ even as a fallback —
"fallback in code" defeats the whole point of the JSON. If a
translation is missing, **fix the JSON**, not the code.
(The one deliberate exception is `wirebugSlotLabel()` in
`panel_player.cpp`: it lives in the block the Core-only reader-test
target compiles and therefore takes its label pair as a parameter,
with the zh literals as defaults. The live panel passes `tr()` values
in at the call site.)

## Adding a new locale

1. Copy the whole `src/resources/i18n/zh-CN/` directory to
   `src/resources/i18n/<new-code>/`.
2. Translate every value. **Keep the keys (left side of `:`) in
   English / dot-path form** — they're identifiers, not content.
3. Add the new files to `src/resources/resources.qrc` (the loader reads
   whatever the qrc exposes).
4. Rebuild. `StringTable::load` doesn't know about specific locales; it
   loads whatever directory the user passes via `--locale` / the conf.

## Schema conventions

| Section           | Purpose                                                  |
|-------------------|----------------------------------------------------------|
| `ui.*`            | overlay panel chrome strings, incl. `ui.reader.*` status lines |
| `ui.demo.*`       | edit-mode demo seeds (player name, ailments, parts, party) |
| `ui.quest_state.*`| quest state labels used by the player panel             |
| `console.*`       | control-console strings (`zh-CN/console.json`)          |
| `mantle.<int>`    | mantle labels keyed by HunterPie SpecializedToolType enum |
| `abnormality.*`   | player-side abnormality labels                          |
| `_meta.*`         | file metadata (loaded but unused at runtime; ignored by the parity check) |

The `mantle.<int>` numbering matches HunterPie 2.14.0.461's
`SpecializedToolType` enum (id 0..19). Adding a new mantle = add a
new key. Renaming an existing one is a HunterPie version bump; do
not do it casually. The `en-US` column is a **translation of the zh
semantics**, not a re-derivation from the enum — that keeps both columns
pointing at the same tool even where the community naming differs.

### Why keys are dot-paths, not arbitrary strings

The `mh::tr("ui.context_hunting")` lookup is one `QHash::constFind`
call. The dotted key is just a string, no parser involved. The
JSON's nested structure is a **readability** feature for humans
editing the file; the loader flattens it once at startup.

If you find yourself wanting `mh::tr("ui")` and getting the whole
`ui` section back as a JSON document, **don't**. The string table
returns leaf strings only. If you need a structured payload,
add a domain reader and pass it through `GameSnapshot`.

## Pluralisation, gender, RTL

The current `QString::arg`-based interpolation does **not** support
ICU plural rules, gender agreement, or RTL bidi handling. The
expected audience is Chinese + English + a couple of Asian
locales, so this is acceptable. If you need full ICU, replace
`mhw::StringTable::tr` with a wrapper that takes ICU arguments and
plumbs them to Qt's `QString::arg` (which already supports `%L1` for
locale-aware numbers, but not grammatical gender).

## How the demo mode interacts with i18n

The edit-mode demo seed (`PlayerPanel::setupDemoData()`,
`MonsterPanel::setupDemoData()`, `DamagePanel::setupDemoData()`) is the
**visual regression baseline**: it is the only way to render every block
of every panel without a running game, so it is what the offscreen
snapshot tools (`tests/snap_*_demo.cpp`, all `--locale`-aware) diff.

As of the runtime-locale work the demo is **localized too**: its labels
read the same keys the live path reads (`ui.demo.*`, plus
`ui.monster_header`, `ui.player_zone`, … for the surrounding chrome).
Two consequences:

- **Within a locale, key and display cannot drift**: the demo no longer
  holds a hardcoded copy that could fall out of sync with the JSON — it
  reads the same table. If you change `ui.player_zone` from `区域` to
  `Zone:`, the demo changes with it, and so does the live panel.
- **Across locales the demo changes**: `snap-all-demo out.png --locale en-US`
  renders the same structure with English labels. The zh baseline is
  preserved byte-for-byte by translating, not rewriting: every
  `ui.*` key added for the port carries the *exact* former C++ literal
  as its zh value (pixel-diffed before/after, see `ws-c/evidence/`).

The one intentional non-table string is the demo monster's *internal
name* fallback: the demo seeds `m.id = 1` and the meta line renders
`em\em001 · <address>`, i.e. an ASCII identity that is obviously not a
live game string. Its display name (`ui.demo.monster_name`) *is*
translated (`火龙` / `Rathalos`), so nothing in the demo pretends to come
from the reader.
